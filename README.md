# 팀 프로젝트 팀 편성 웹 앱 (중간 과제)

학생이 팀에 지원하고 팀원이 투표해 팀을 꾸리는 Streamlit 웹 앱. 모집을 마감한 뒤 팀이 없는 학생은 오픈라우터의 AI가 배정안을 내고, 앱이 그 배정안을 규칙으로 검사한다.

https://study04teamformation-datascience.streamlit.app/

## 3. 고른 해결 방법

공고 3장의 기능 8개를 모두 어려운 해결로 만들었다.

| 기능 | 고른 해결 | 구현 위치 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결(`st.fragment(run_every=3)`로 팀 목록, 지원, 투표 단추, 팀이 없는 학생을 3초마다 다시 그림) | `streamlit_app.py`의 `student_board`, `admin_board` |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결(지원 단계에서 필수 포함 역할을 채울 자리가 모자라게 되는 지원을 막음) | `rules.required_slot_ok`, `rules.apply_block_reason` |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결(승인 직전에 정원, 주 역할 중복, 필수 포함 역할 자리를 다시 검사함. 투표가 끝난 순서로 처리) | `rules.recheck_reason`, `service.vote` |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결(DB 유일성 제약: `tf_members`의 기본 키 `(team_id, slot_no)`, `student_id` 유일, 대기 지원 학생당 1개) | `schema.sql` |
| AI 응답이 늦을 때 | 어려운 해결(모델마다 부른 때부터 응답을 다 받을 때까지 120초 전체 대기 시간을 재서 끊고 다음 모델로 넘어감) | `ai.call_with_deadline`, `ai.run_assignment` |
| 3차 모델까지 실패 | 어려운 해결(검사 다섯 가지를 모두 통과하는 배정을 모든 경우를 따져 끝까지 찾음. 배정이 없으면 이유를 보여 줌) | `rules.find_assignment`, `rules.infeasibility_reasons` |
| AI 대기 중 화면 | 어려운 해결(`assign_status`에 "2차 모델(…)의 응답을 기다리는 중 (35초 / 120초)"처럼 몇 차 모델을 몇 초째 기다리는지 1초마다 보여 줌) | `streamlit_app._run_assign` |
| DB(Supabase)가 일시정지되지 않게 | 어려운 해결(외부 예약 서비스인 GitHub Actions가 매일 한국 시각 09:00에 DB에 질의를 보냄) | `.github/workflows/keep-db-awake.yml` |

- 1차 `cohere/north-mini-code:free`
- 2차 `poolside/laguna-s-2.1:free`
- 3차 `google/gemma-4-31b-it:free`

## 5. 오픈라우터 AI 모델 호출 실패 사례

### 사례 1: 배포한 앱에서 1차 빈 응답, 2차와 3차 HTTP 429로 모두 실패해 앱 자체 배정으로 넘어감

- 언제: 2026-10-30 16:30~16:31(한국 시각), 배포한 앱에서 부록 3(어려움) 15단계 "관리자가 배정, 확정"을 할 때
- 무슨 일: 1차 모델 `cohere/north-mini-code:free`가 50.3초 만에 빈 응답을 냄 → 2차 `poolside/laguna-s-2.1:free`가 HTTP 429 → 3차 `google/gemma-4-31b-it:free`도 HTTP 429. 3차까지 실패하자 앱이 모든 경우를 따져 찾은 배정을 씀. result는 `승인: 배정안을 만듦(앱 자체 배정)`, 확정한 뒤 새 브라우저에서 네 팀 모두 규칙을 지킴.
- 화면: [img/2026-10-30 배포 앱 AI 호출 기록.png](img/2026-10-30%20배포%20앱%20AI%20호출%20기록.png)(관리자 화면의 "AI 호출 기록")
- 기록: [docs/검증 기록/2026-10-30 배포 앱 E2E.md](docs/검증%20기록/2026-10-30%20배포%20앱%20E2E.md)의 어려움 시나리오 27번 항목(파일 81번째 줄)

### 사례 2: 1차 모델이 120초 안에 응답하지 않아 끊고, 2차 모델의 배정안은 규칙 위반이라 앱이 걸러 냄

- 언제: 2026-10-30, 내 컴퓨터에서 부록 2(중간) 11단계 "관리자가 배정, 확정"을 할 때(배정에 130초 걸림)
- 무슨 일: assign_status에 차례로 남음.
  - `1차 모델(cohere/north-mini-code:free) 실패: 120초 안에 응답 없음`
  - `2차 모델(poolside/laguna-s-2.1:free) 실패: 검사 통과 못 함: 팀2: 기획자와 웹 프로그래머를 서로 다른 학생이 맡을 수 없음; 팀3: 주 역할 기획자 중복`
  - `3차 모델(google/gemma-4-31b-it:free) 실패: HTTP 429`
  - `배정안을 만든 곳: 앱 자체 배정`
- 기록: [docs/검증 기록/2026-10-30 로컬 E2E 최종.md](docs/검증%20기록/2026-10-30%20로컬%20E2E%20최종.md)의 중간 시나리오 19번 항목(파일 49번째 줄)

### 사례 3: 모델을 고를 때 무료 모델 13개 가운데 12개가 실패

2026-10-29 저녁에 어려움 시나리오의 마감 직후 상태로 무료 모델을 한 번씩 불렀을 때, 120초 초과, HTTP 429, HTTP 403, 빈 응답, JSON으로 읽을 수 없는 응답이 모두 나왔고 규칙을 지키는 배정안을 낸 것은 `cohere/north-mini-code:free` 하나뿐이었다(표: [docs/사례 기록.md](docs/사례%20기록.md), 스크립트: [tools/try_models.py](tools/try_models.py)).

## 6. 클로드가 잘못된 추론이나 답변을 한 사례

### 사례 1: DB 연결 풀을 잘못 설계해, 학생이 9명을 넘으면 단추를 눌러도 처리되지 않음

- 무엇: 클로드가 구현 계획([docs/구현 계획.md](docs/구현%20계획.md) Task 4)에서 연결 풀을 `ThreadedConnectionPool(1, 8)`로 정하면서 "연결을 한 번 만들고 다시 쓴다"고 추론함. 그런데 psycopg2의 풀은 쉬는 연결을 최소 개수(1개)만 남기고 돌려받을 때마다 닫기 때문에, 화면을 다시 그릴 때마다 새 연결을 맺었고, 그동안 풀 전체가 잠겨 다른 학생의 단추 처리가 줄을 섬.
- 알아챈 방법: 채점 방식 검증(e2e)에서 부록 2(중간) 7단계(학생11이 팀4에 지원)와 부록 3(어려움) 6단계 뒤(학생6의 지원, 학생2의 찬성 등)의 클릭이 처리되지 않아 result가 앞 단계 안내로 남았음. 그래서 학생 16명이 차례로 로그인하자마자 지원하게 해 보니 8번째까지는 정상이고 9번째부터 모두 실패함. 앱의 실행 흐름을 10초마다 기록해 `psycopg2.connect`를 하는 동안 다른 흐름들이 `putconn`의 잠금을 기다리는 것을 확인함.
- 고친 곳: 커밋 98a5200(최소 개수를 8로). 테스트 `test_pool_reuses_connections_instead_of_reconnecting`이 고치기 전에는 연결 21개 생성으로 실패하고, 고친 뒤 통과함. 고친 뒤 세 시나리오 불일치 0건: [docs/검증 기록/2026-10-30 로컬 E2E 최종.md](docs/검증%20기록/2026-10-30%20로컬%20E2E%20최종.md), [배포 앱](docs/검증%20기록/2026-10-30%20배포%20앱%20E2E.md)

### 사례 2: Supabase 지역을 서울로 안내함

- 무엇: 클로드가 Supabase 프로젝트를 만들 때 Region을 Northeast Asia (Seoul)로 고르라고 안내함. 앱은 Streamlit Community Cloud(미국)에서 돌기 때문에 DB가 서울에 있으면 질의마다 태평양을 왕복함.
- 알아챈 방법: DB 연결 코드를 설계하며 질의 왕복 시간을 따지다가, Streamlit 문서(Status and limitations of Community Cloud)에서 모든 앱이 미국에서 호스팅된다는 것을 확인함.
- 고친 곳: 미국(Americas, East US Ohio)으로 다시 안내했고, 화면 한 번에 DB 질의가 한 번만 가도록 `service.load_snapshot`을 설계함(기록: [docs/사례 기록.md](docs/사례%20기록.md), 커밋 1a34192).

## 7. 앱에서 발견한 문제점이나 개선 필요 사항

문제 1, 2는 연습용 시나리오를 채점 방식 그대로 돌리는 스크립트([e2e/run_scenarios.py](e2e/run_scenarios.py))로, 문제 3은 배포한 앱의 관리자 화면을 캡처하다 찾았다.

### 문제 1: 부록 2(중간) 8단계에서 "이어서 팀3에도 지원"의 결과가 앞의 "대기"로 남음

- 단계: 학생12(PT;RW;FD)가 팀4에 지원(대기)한 뒤 이어서 팀3에 지원(기대: 막힘)
- 증상: 팀3 지원의 result가 `대기: 팀원의 투표를 기다림`으로 남아 기대(막힘)와 다름
- 원인: 단추를 누르면 result를 먼저 그리고 그 아래 지원 단추를 나중에 그려서, result가 바뀐 직후 잠깐 팀3 지원 단추가 활성으로 남아 있었고 그때 누른 클릭이 처리되지 않음
- 근거와 고친 곳: [docs/검증 기록/2026-10-29 로컬 E2E.md](docs/검증%20기록/2026-10-29%20로컬%20E2E.md)의 "1. 고치기 전" 15번 항목(파일 25번째 줄, `기대 막힘 / 실제 대기 | 불일치`), 커밋 7e1f7fa(result를 화면 맨 끝에 채움). 고친 뒤 같은 단계: 같은 파일 "3. 고친 뒤"의 중간 시나리오 15번 항목(`기대 막힘 / 실제 막힘 | 일치`)

### 문제 2: 부록 1(쉬움) 6단계에서 배정안 확정을 눌러도 result가 바뀌지 않음

- 단계: 관리자가 마감하고 AI 배정을 한 뒤 배정안 확정을 누름(검증 출력 17번 항목)
- 증상: 확정은 DB에 저장됐지만 result가 앞 단계의 `승인: 배정안을 만듦(…)`으로 남고, 18번 항목(새 브라우저에서 팀 구성 검사)도 팀을 읽지 못함
- 원인: 화면을 다시 그리다 DB 연결을 잠깐 얻지 못해 오류가 났고, result를 그리기 전에 멈춤
- 고친 곳: 커밋 df3b70c(DB 오류를 잡아 안내하고, 단추 결과는 반드시 그림)

### 문제 3: 배포한 앱의 AI 호출 기록에서 모델 이름이 그림문자로 바뀌어 보임

- 단계: 배포한 앱에서 부록 3(어려움) 15단계(관리자가 배정, 확정)를 마친 뒤 관리자 화면의 "AI 호출 기록"을 엶
- 증상: `cohere/north-mini-code:free`가 `cohere/north-mini-code🆓`로 보임(마크다운이 `:free:`를 그림문자로 바꿈). 사례 5-1의 화면을 캡처하다 발견함
- 고친 곳: 커밋 7bdf552(모델 이름을 코드 글꼴로 감쌈). 고친 뒤 화면: 위 사례 5-1의 그림

### 남은 개선 필요 사항

- AI 배정을 기다리는 동안(최대 약 6분) 관리자가 다른 관리자 단추를 누르면 Streamlit이 진행 중인 실행을 멈추고 새로 실행하므로, 그때까지의 AI 배정은 버려지고 다시 눌러야 함. 지금은 result에 `AI 배정 중: 결과를 기다리는 중`을 보여 기다리게 할 뿐, 배정을 따로 계속 돌리지는 못함.
- 같은 학생이 브라우저 두 개로 같은 순간에 서로 다른 팀에 지원하면, 서로 다른 팀 행만 잠그기 때문에 두 지원이 함께 들어갈 수 있음(학생 행도 잠그면 막을 수 있음). 학생마다 브라우저 하나를 쓰는 채점에서는 생기지 않음.

## 실행 방법(내 컴퓨터)

```bash
pip install -r requirements.txt
streamlit run streamlit_app.py
```

`.env`에 `OPENROUTER_API_KEY`, `DATABASE_URL`(Supabase Session pooler), `ADMIN_PASSWORD`를 넣는다. 값은 커밋하지 않는다.

테스트: `python -m pytest -q`

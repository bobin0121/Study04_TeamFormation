# 팀 편성 웹 앱 PRD

- 작성일: 2026-10-28
- 상태: 사용자 검토 대기
- 근거: 「중간 과제 공고: 팀 프로젝트를 위한 팀을 편성하는 웹 앱 만들기」(이하 "공고"). 이 문서와 공고가 다르면 공고를 따른다.

## 1. 개요

### 1.1 무엇을

학생들이 팀 프로젝트 팀을 스스로 편성하는 웹 앱이다. 학생은 팀에 지원하고, 팀원은 지원에 찬성하거나 거부한다. 모집을 마감한 뒤 팀이 없는 학생은 AI(오픈라우터)가 배정안을 내고, 앱이 그 배정안을 규칙으로 검사한다.

### 1.2 누가

| 사용자 | 하는 일 |
|---|---|
| 학생(가상 명단의 학생) | 학번과 비밀번호(모두 `1234`)로 로그인한다. 팀 목록과 팀원의 주 역할, 보조 역할을 본다. 팀에 지원한다. 내 팀에 들어온 지원에 찬성 또는 거부를 누른다. |
| 관리자(교수) | 학번 `admin`으로 로그인한다. 명단 CSV와 팀 수를 넣어 처음 상태를 만든다. 모집을 마감한다. 배정안을 받아 확인하고 확정한다. |

### 1.3 왜 이 문서가 중요한가

채점은 자동 채점 프로그램이 배포한 앱을 화면의 `key`로 조작해서 한다(공고 2.7절, 6.2절). 그래서 화면 요소의 `key`와 결과 안내의 첫 단어("승인", "대기", "거절", "막힘")가 공고와 한 글자라도 다르면 점수를 잃는다. 이 문서는 그 약속을 빠짐없이 적는다.

채점 프로그램이 화면을 읽는 방식(공고 2.7절, 6.2절에서 옮김):

- 학생마다 브라우저를 따로 열고, 단계마다 **단추를 누른 사람의 화면**에 있는 `result`의 첫 단어를 읽는다. 지원 단추를 누르면 그 지원의 결과, 찬성이나 거부 단추를 누르면 그 지원의 지금 상태(승인, 대기, 거절)다. 한 단계에 동작이 여럿이면 동작마다 확인한다.
- 안내 형식은 공고의 예와 같은 `막힘: 같은 주 역할의 팀원이 있음`(첫 단어 바로 뒤에 쌍점과 공백)이다.
- 지원 단추가 **없거나 비활성이면 "막힘"으로 본다.** 그래서 이미 팀이 있음, 결과를 기다리는 지원이 있음, 모집 마감 때는 단추를 비활성화해도 된다(공고가 그렇게 하라고 정함).
- 단추가 나타나기를 7초까지 기다린다. 화면을 다시 열지 않는다.
- 마감 결과(거절된 지원, 팀에서 빠진 학생)는 관리자 화면의 `unassigned`로 확인한다.
- 마지막에 브라우저를 새로 열어 확정한 팀 구성이 남아 있고 규칙을 지키는지 검사한다.
- AI 배정이 10분을 넘으면 채점자가 끊는다(공고 6.3절 18번). 이 앱은 최대 6분 남짓이다.

명단 CSV의 역할 열은 한국어 역할 이름(`기획자` 등)이다. `학생1(PL;RW)` 같은 괄호 속 약자는 이름 열의 일부일 뿐이고 앱은 해석하지 않는다. 연습 시나리오 3개의 명단과 단계, 기대 결과는 공고 부록에 있고, 시나리오 테스트(10장)에 그대로 옮긴다.

### 1.4 목표

- 공고 3장의 기능 8개를 모두 **어려운 해결**로 만든다(5장).
- 연습용 시나리오 3개(쉬움, 중간, 어려움)의 모든 단계에서 결과 안내의 첫 단어가 기대 결과와 같다.
- 공개하지 않은 채점 시나리오(학생 8~16명, 팀 3~4개)에서도 같은 규칙으로 맞게 동작한다. 연습용 시나리오의 이름이나 순서에 맞춘 코드는 쓰지 않는다(공고 6.3절 19번).

### 1.5 하지 않는 것

- 구글 로그인(`st.login`)은 쓰지 않는다.
- 학생 회원 가입, 비밀번호 바꾸기, 명단 편집 화면은 만들지 않는다. 명단은 CSV로만 바꾼다.
- 새로 고침 단추(`refresh`)는 두지 않는다. 자동 갱신(어려운 해결)을 쓰기 때문이다.
- 무료 모델 자동 라우터(`openrouter/free`)는 쓰지 않는다(공고 6.3절 14번).

### 1.6 실패로 보는 것(기능이 돌아가도 안 되는 것)

- 키, DB 주소, 관리자 비밀번호가 코드, 커밋 기록, 화면에 나타남
- 비밀번호를 해시하지 않고 저장함
- 학생 계정으로 관리자 기능을 쓸 수 있음
- AI 배정이 10분 넘게 끝나지 않음
- README의 사례를 꾸며 냄

## 3. 데이터(DB)

공고 5장의 최소 참고안을 따르고, 필요한 열과 테이블을 더한다. 모든 테이블 이름은 `tf_`로 시작한다.

| 테이블 | 열 | 제약 |
|---|---|---|
| `tf_students` | `id`, `student_no`, `name`, `main_role`, `password_hash`, `is_admin` | `student_no` 유일. `main_role`은 6개 역할 가운데 하나(관리자는 비움) |
| `tf_student_sub_roles` | `student_id`, `role` | 기본 키 `(student_id, role)`. `role`은 6개 역할 가운데 하나 |
| `tf_teams` | `id`(=팀 번호), `name` | `name` 유일. `id`는 1, 2, …로 명단 올릴 때 정한다. |
| `tf_members` | `team_id`, `slot_no`, `student_id` | 기본 키 `(team_id, slot_no)`, `student_id` 유일, `check (slot_no between 1 and 4)` |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`, `reason`, `created_at`, `decided_at` | `status`는 대기, 승인, 거절 가운데 하나. **대기 중인 지원은 학생당 1개**(부분 유일 인덱스) |
| `tf_votes` | `application_id`, `voter_id`, `vote`, `created_at` | 기본 키 `(application_id, voter_id)`. `vote`는 찬성, 거부 가운데 하나 |
| `tf_settings` | `key`, `value` | 마감 여부, 확정 여부, 확정 전 배정안(JSON) |
| `tf_ai_logs` | `id`, `model`, `attempt`, `outcome`, `detail`, `elapsed_sec`, `created_at` | AI 호출 기록. README 사례(공고 7.1절 5항)의 근거가 된다. |

- 시각은 `timestamptz`로 저장한다. 화면에 시각을 보여 줄 때는 한국 시각으로 바꾼다(배포 서버는 UTC).
- `schema.sql`은 앱이 실제로 쓰는 테이블, 열, 제약과 같아야 한다. 앱이 시작할 때 `schema.sql`을 그대로 실행해(`create ... if not exists`) 테이블을 만든다. 그래서 둘이 어긋날 수 없다.
- 연결은 프로세스당 연결 풀 하나를 `st.cache_resource`로 만들어 다시 쓴다. 죽은 연결은 풀을 새로 만들어 복구한다(교수 예제 recipe4fridge의 방식).
- 채점 때는 학생 브라우저 여러 개가 2초마다 동시에 화면을 다시 그린다. 풀의 연결이 모두 쓰이는 중이면 오류를 내지 않고 빈 연결이 생길 때까지 기다린다.

## 4. 규칙(공고 2.3~2.5절을 코드로 옮긴 것)

역할 6개: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자.
필수 포함 역할 2개: 기획자, 웹 프로그래머.

### 4.1 기본 정의

- **맡을 수 있는 역할** = 주 역할 + 보조 역할
- **주 역할 중복**: 한 팀에 주 역할이 같은 학생이 2명 이상이면 안 된다. 보조 역할은 중복을 따지지 않는다.
- **채운 필수 역할 수**: 팀원 가운데 기획자를 맡을 사람과 웹 프로그래머를 맡을 사람을 **서로 다른 사람**으로 고를 때 채울 수 있는 최대 개수(0, 1, 2). 한 학생이 둘 다 맡을 수 있어도 하나로만 센다.
  - 2개: 기획자를 맡을 수 있는 사람 p와 웹 프로그래머를 맡을 수 있는 사람 w가 있고 p ≠ w
  - 1개: 위가 안 되지만 둘 가운데 하나는 맡을 사람이 있음
  - 0개: 아무도 없음
- **필수 역할 자리 검사**: 지원자가 들어간 뒤 남는 자리 수(4 − 들어간 뒤 인원)가 채우지 못한 필수 역할 수(2 − 채운 필수 역할 수)보다 적으면 어긴 것이다(공고 3장 "필수 포함 역할 자리 계산").
  - 채운 필수 역할 수는 **지원자를 넣은 팀**으로 센다. 지원자가 모자란 역할을 맡을 수 있으면 그만큼 채운 것으로 본다. 예: 테스터와 발표자만 있는 팀(2명)에 기획자가 지원하면, 남는 자리 1개, 채우지 못한 필수 역할 1개(웹 프로그래머)이므로 막지 않는다. 같은 팀에 보고서 작성자가 지원하면 남는 자리 1개, 채우지 못한 필수 역할 2개이므로 막는다(공고의 예).
  - 공고 문장 "그 팀에서 아직 채우지 못한"은 지원자를 빼고 센다고도 읽을 수 있다. 그렇게 읽으면 위 예의 기획자 지원도 막혀서, 필수 역할을 채워 줄 학생이 들어오지 못한다. 그래서 지원자를 넣고 센다. 연습 시나리오의 기대 결과(부록 3의 10단계 승인, 11단계 막힘)는 두 해석 모두와 맞는다.

### 4.2 지원 단추를 누를 때(막힘 검사)

아래 순서로 검사해 처음 걸린 이유를 보여 준다. 걸리면 DB에 기록하지 않는다.

| 순서 | 조건 | 안내 |
|---|---|---|
| 1 | 모집이 마감됨 | `막힘: 모집이 마감됨` |
| 2 | 이미 팀이 있음 | `막힘: 이미 팀이 있음` |
| 3 | 결과를 기다리는 지원이 있음 | `막힘: 결과를 기다리는 지원이 있음` |
| 4 | 팀이 4명 | `막힘: 팀이 꽉 참` |
| 5 | 주 역할이 같은 팀원이 있음 | `막힘: 같은 주 역할의 팀원이 있음` |
| 6 | 필수 역할 자리 검사에 걸림 | `막힘: 필수 포함 역할(기획자, 웹 프로그래머)을 맡을 학생의 자리가 모자람` |

통과하면:
- 빈 팀: 바로 팀원이 된다. `승인: 팀N에 들어감`
- 팀원이 있는 팀: 지원을 대기로 기록한다. `대기: 팀원의 투표를 기다림`

1~3번에 해당하면 지원 단추를 아예 비활성화한다(공고 2.8절). 4~6번은 단추를 누른 뒤 "막힘" 안내로 막는다.

### 4.3 투표

- 투표할 수 있는 사람은 **투표하는 때의** 그 팀 팀원이다. 지원한 뒤 새로 들어온 팀원도 투표한다.
- 한 번 투표하면 바꿀 수 없다. 투표한 지원에는 단추 대신 `내 투표: 찬성`처럼 보여 준다.
- 거부가 하나라도 나오면 다른 팀원을 기다리지 않고 바로 거절한다. `거절: 팀원이 거부함`
- 지금 팀원 모두가 찬성하면 **승인 직전 검사**를 한다(4.4절).
- 아직 투표하지 않은 팀원이 있으면 대기다. `대기: 다른 팀원의 투표를 기다림`
- 마감 뒤에는 투표할 수 없다(단추를 보여 주지 않는다).

### 4.4 승인 직전 검사(어려운 해결)

모든 팀원이 찬성해 승인하려는 순간, 팀을 잠근 상태에서 다시 검사한다.

| 조건 | 안내 |
|---|---|
| 팀이 4명 | `거절: 승인 직전 검사에서 팀이 꽉 참` |
| 주 역할이 같은 팀원이 있음 | `거절: 승인 직전 검사에서 같은 주 역할의 팀원이 있음` |
| 필수 역할 자리 검사에 걸림 | `거절: 승인 직전 검사에서 필수 포함 역할을 맡을 학생의 자리가 모자람` |
| 모두 통과 | `승인: 팀N에 들어감` |

- 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다.
- 승인 직전 검사 전에는 대기 중인 지원을 미리 거절하지 않는다.

### 4.5 마감

관리자가 "모집 마감"을 누르면 한 트랜잭션에서 다음을 한다(공고 2.5절 1~2항).
1. 마감 표시를 한다. 그 뒤로 지원과 투표를 할 수 없다.
2. 대기 중인 지원을 모두 거절한다(이유: 모집 마감).
3. 팀원이 1명뿐인 팀의 학생을 팀에서 뺀다. 이 학생은 "팀이 없는 학생"이 된다.

안내: `승인: 모집을 마감함`. 이미 마감했으면 `막힘: 이미 마감됨`.

### 4.6 배정안 검사(다섯 가지)

배정안은 팀이 없는 학생만 팀에 넣는다. 이미 팀에 있는 학생은 옮기지 않는다. 앱은 AI의 배정안이든 앱이 만든 배정안이든 똑같이 다음 다섯 가지로 검사한다.

1. 팀이 없는 학생이 빠짐없이 배정됨(배정안에 없는 학생이나 원래 팀이 있는 학생이 들어 있으면 실패)
2. 한 학생은 한 팀에만 배정됨
3. 모든 팀이 2~4명
4. 팀 안에서 주 역할 중복 없음
5. 모든 팀에 기획자와 웹 프로그래머를 서로 다른 사람이 맡음(보조 역할 포함)

검사에 실패하면 어느 검사에서 왜 실패했는지 기록하고 다음 모델로 넘어간다.

### 4.7 모든 경우를 따지는 배정(어려운 해결)

팀이 없는 학생을 한 명씩 팀에 넣어 보며 되돌아가는 탐색(백트래킹)으로, 4.6절 다섯 가지를 모두 통과하는 배정을 끝까지 찾는다.

- 넣을 때마다 정원(4명)과 주 역할 중복을 바로 확인해 안 되는 갈래는 더 보지 않는다.
- 빈 팀끼리는 서로 바꿔도 같은 배정이므로, 빈 팀 가운데 첫 번째에만 넣어 본다.
- 남은 학생 수로 2명이 안 된 팀을 채울 수 없으면 그 갈래를 버린다.
- 배정이 있으면 반드시 찾고, 없으면 "없음"을 확정한다.

### 4.8 규칙을 지키는 배정이 없을 때

"AI 배정"을 누르면 AI를 부르기 전에 4.7절 탐색으로 배정이 있는지 먼저 확인한다. 없으면 AI를 부르지 않고 `assign_status`에 `규칙을 지키는 배정이 없음`과 이유를 보여 준다. 이유는 찾을 수 있는 만큼 구체적으로 적는다.

- 4명이 다 찬 팀에 필수 역할을 맡을 사람이 없음: `팀3에 웹 프로그래머를 맡을 학생이 없음`
- 팀이 없는 학생 가운데 그 팀에 들어갈 수 있으면서(주 역할 중복 없음) 모자란 역할을 맡을 학생이 없음: `팀2에 기획자를 맡을 학생이 없음`
- 전체 학생 수가 팀 수 × 2보다 적거나 팀 수 × 4보다 많음: `학생 수로는 모든 팀을 2~4명으로 만들 수 없음`
- 위에 해당하지 않음: `역할 조합으로는 모든 규칙을 함께 지킬 수 없음`

`result`에는 `막힘: 규칙을 지키는 배정이 없음`을 보여 준다.

## 5. 어려운 해결 8개

| 기능(공고 3장) | 이 앱의 해결 |
|---|---|
| 다른 사람의 변경 보기 | 팀 목록, 지원, 투표 단추, 팀이 없는 학생 표시를 `st.fragment(run_every=...)`로 감싸 **2초마다** 바뀐 부분만 다시 그린다(공고: 5초 이하). |
| 필수 포함 역할을 지킬 수 없는 팀 | 지원 단계에서 4.1절 필수 역할 자리 검사로 막는다(4.2절 6번). 승인 직전에도 같은 검사를 한다. |
| 같은 팀에 대기 중인 지원이 여럿 | 승인 직전 검사(4.4절). 투표가 끝난 순서대로 처리한다. |
| 마지막 자리에 두 명이 동시에 들어감 | `tf_members`의 기본 키 `(team_id, slot_no)`와 `student_id` 유일 제약으로 먼저 도착한 학생만 기록한다. 지원과 투표 처리는 팀 행을 잠그고(`select ... for update`) 한다. 대기 지원 학생당 1개도 DB 제약으로 지킨다. |
| AI 응답이 늦을 때 | 모델마다 **부른 때부터 응답을 다 받을 때까지 120초**를 잰다. 요청을 별도 스레드에서 보내고 120초가 지나면 기다리지 않고 다음 모델로 넘어간다. 응답이 천천히 와도 120초를 넘기지 않는다. |
| 3차 모델까지 실패 | 4.7절 탐색으로 앱이 배정한다. |
| AI 대기 중 화면 | `assign_status`에 `2차 모델(모델 이름)의 응답을 기다리는 중 (35초 / 120초)`처럼 몇 차 모델을 몇 초째 기다리는지 1초마다 보여 준다. 실패한 모델과 실패 이유도 줄마다 남긴다. |
| DB 일시정지 막기 | GitHub Actions 예약 작업이 매일 한 번 DB에 `select`를 보낸다. DB 주소는 저장소 Secrets에 두고 출력하지 않는다. 손으로 돌려 보는 실행(`workflow_dispatch`)도 둔다. |

- 전체 배정 시간의 상한: 3개 모델 × 120초 + 탐색(수 초) ≈ 6분 남짓. 10분을 넘지 않는다(공고 6.3절 18번).

## 6. AI 배정

### 6.1 흐름

1. 마감했는지, 이미 확정했는지 확인한다. 마감 전이면 `막힘: 모집을 먼저 마감해야 함`, 확정했으면 `막힘: 이미 확정함`.
2. 4.7절 탐색으로 배정이 있는지 확인한다. 없으면 4.8절.
3. 팀이 없는 학생이 0명이고 지금 팀 구성이 규칙을 지키면 빈 배정안을 만든다.
4. 1차 모델을 부른다. 응답이 없음(120초 초과), 빈 응답, 오류(HTTP 429 등), JSON 해석 실패, 4.6절 검사 실패 가운데 하나면 2차, 3차로 넘어간다.
5. 3차까지 실패하면 2번에서 찾은 앱의 배정을 쓴다.
6. 검사를 통과한 배정안만 관리자에게 보여 준다. 표의 열은 학생 이름, 주 역할, 보조 역할, 배정된 팀, 그리고 배정안을 만든 곳(예: "2차 모델 …", "앱 자체 배정")이다. 배정안은 DB(`tf_settings`)에 저장해 화면을 다시 그려도 남게 한다.
7. 관리자가 "배정안 확정"을 누르면, 상태가 그사이 바뀌지 않았는지(마감 상태, 팀이 없는 학생 목록) 확인하고 다섯 가지 검사를 한 번 더 한 뒤 `tf_members`에 저장한다. `승인: 배정안을 확정함`

`result` 안내: 배정안을 만들었으면 `승인: 배정안을 만듦(2차 모델)`, 앱 자체 배정이면 `승인: 배정안을 만듦(앱 자체 배정)`.

### 6.2 요청과 응답

- 보내는 것: 팀마다 팀원(학번, 이름, 주 역할, 보조 역할), 팀이 없는 학생(같은 항목), 공고 2.3절의 규칙. 비밀번호는 보내지 않는다.
- 받는 것: JSON `{"assignments": [{"student_no": "2026303", "team": 3}, ...]}`. 응답에 다른 글이나 코드 블록 표시가 섞여도 JSON 부분만 꺼내 읽는다.
- 요청 설정: `reasoning`의 effort를 low로, `max_tokens`를 넉넉히 준다(공고 4.3절).
- 모델 3개는 구현 단계에서 오픈라우터 무료 모델(`:free`) 가운데 실제로 이 요청에 배정안을 잘 내는 것을 시험해 고르고 README에 적는다.
- 오류 안내에는 HTTP 상태와 짧은 이유만 쓴다. 요청 머리글(키가 들어 있음)은 기록하지도 출력하지도 않는다.

## 7. 화면

### 7.1 공통

- 로그인하지 않았으면 로그인 화면만 보인다.
- 로그인 정보는 브라우저 탭마다 따로 둔다(`st.session_state`). 채점 프로그램이 학생마다 브라우저를 따로 열기 때문이다.
- `result`의 안내는 다음 동작을 할 때까지 남아 있어야 한다. 자동 갱신으로 지워지지 않게 세션에 저장해 두고 매번 다시 그린다.
- 로그아웃 단추를 둔다.

### 7.2 화면 이름 표(공고 2.7절, 한 글자도 바꾸지 않음)

| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input`(type=password) | `login_password` |
| 로그인 단추 | `st.form_submit_button` | `login_submit` |
| 로그인한 사람 표시 | `st.container` | `whoami` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시 | `st.container` | `team_1`, `team_2`, … |
| 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 지원에 찬성하는 단추 | `st.button` | `vote_yes_{지원자 학번}` |
| 지원에 거부하는 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 명단으로 처음 상태 만들기 단추 | `st.button` | `admin_start` |
| 모집 마감 단추 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시 | `st.container` | `unassigned` |
| AI 배정 단추 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 단추 | `st.button` | `admin_confirm` |

- 표에 없는 요소에는 이 이름들과 겹치지 않는 key를 쓴다.
- 한 학생에게 대기 중인 지원은 1개뿐이므로 `vote_yes_{학번}`은 한 화면에서 겹치지 않는다.

### 7.3 로그인 화면

- 학번, 비밀번호, 로그인 단추(폼 하나)
- 틀리면 `학번이나 비밀번호가 맞지 않음.`을 보여 준다. 학번이 없는 경우와 비밀번호가 틀린 경우를 구분하지 않는다.

### 7.4 학생 화면

- `whoami`: `학생3(PL;TT) (2026303) 로그인함`처럼 이름이 보인다.
- 내 상태 한 줄: `내 팀: 팀2`, `아직 팀이 없음`, `팀1 지원 결과를 기다리는 중` 가운데 하나. 마감했으면 `모집이 마감됨`도 함께 보여 준다.
- `result`
- 팀 목록: 팀마다 `team_N` 컨테이너에 팀 이름, 인원(예: 3/4), 내 팀이면 "내 팀" 표시, 팀원마다 이름, 주 역할, 보조 역할을 보여 준다. 그 아래에 `apply_N` 단추를 둔다.
  - 이미 팀이 있음, 결과를 기다리는 지원이 있음, 모집 마감이면 모든 지원 단추를 비활성화한다.
- 내 팀에 들어온 지원(내가 팀원일 때만): 대기 중인 지원마다 지원자 이름, 역할, 지금까지의 투표 수를 보여 주고, 내가 투표하지 않았으면 `vote_yes_{학번}`, `vote_no_{학번}`을, 투표했으면 `내 투표: 찬성` 또는 `내 투표: 거부`를 보여 준다.
- 위의 팀 목록과 지원 영역, `result`는 2초마다 다시 그리는 fragment 안에 둔다.

### 7.5 관리자 화면

- `whoami`: `관리자 (admin) 로그인함`
- `result`
- 명단 올리기: `admin_roster_file`, `admin_team_count`(1 이상, 기본값 3), `admin_start`
  - 성공: `승인: 명단 16명과 팀 4개로 처음 상태를 만듦`
  - CSV 오류: `막힘: CSV 5번째 줄의 주 역할이 6개 역할에 없음`처럼 줄과 이유를 보여 주고 DB는 바꾸지 않는다.
  - 파일을 고르지 않음: `막힘: 명단 CSV 파일을 골라야 함`
- 모집 마감: `admin_close`
- 팀 목록(`team_N`, 학생 화면과 같은 모양, 지원 단추 없음)과 `unassigned`(팀이 없는 학생의 이름과 역할)
- AI 배정: `admin_assign`, `assign_status`(진행 안내, 실패한 모델과 이유, 배정이 없을 때의 안내)
- 배정안 표와 `admin_confirm`. 배정안이 없으면 확정 단추를 비활성화하거나 누를 때 `막힘: 확정할 배정안이 없음`
- 팀 목록과 `unassigned`는 2초마다 다시 그린다. 관리자 단추가 오래 걸리는 동작(AI 배정)을 하는 동안 자동 갱신이 그 동작을 끊지 않게 한다(구현할 때 실제로 확인한다).

## 8. 명단 CSV

- 열: `student_no,name,main_role,sub_roles`(머리글 줄 필수)
- `utf-8-sig`로 읽어 BOM이 있어도 읽는다.
- `sub_roles`는 0~2개이고 `;`로 나눈다. 비어 있으면 보조 역할이 없다.
- 검사: 열이 4개인지, 학번이 비어 있거나 겹치지 않는지, 학번이 `admin`이 아닌지, 역할이 6개 가운데 하나인지, 보조 역할이 2개 이하인지
- 처음 상태 만들기: 한 트랜잭션에서 투표, 지원, 팀원, 팀, 설정, 관리자가 아닌 학생과 보조 역할을 모두 지우고, 명단의 학생(비밀번호 `1234`의 해시)과 팀1~팀N을 만든다. 관리자 계정은 남긴다. AI 호출 기록(`tf_ai_logs`)은 남긴다.

## 9. 보안과 키

- `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 `.env`(내 컴퓨터)와 Streamlit Secrets(배포)에만 둔다. `.gitignore`가 `.env`를 거른다. `.env.example`에는 이름만 둔다.
- 코드는 키 값을 출력하지 않는다. 확인이 필요하면 "있음, 없음"만 보여 준다. DB 오류 안내에도 연결 문자열을 넣지 않는다(psycopg2의 `invalid dsn` 오류는 연결 문자열을 메시지에 담으므로 잡아서 일반 문구로 바꾼다). 예상하지 못한 예외의 내용도 화면에 나오지 않게 `client.showErrorDetails`를 끈다.
- 관리자 계정: 앱이 시작할 때 `ADMIN_PASSWORD`로 `admin` 계정을 만든다. 저장된 해시와 다르면 비밀번호를 갱신한다.
- 비밀번호는 bcrypt 해시로만 저장한다.
- 관리자 기능은 화면에서 숨길 뿐 아니라, 처리 함수마다 로그인한 사람이 관리자인지 DB 기준으로 다시 확인한다.
- 실제 사람의 이름과 학번은 쓰지 않는다. 테스트도 가상 명단만 쓴다.
